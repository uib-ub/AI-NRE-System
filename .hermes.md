# AI-NER-System Hermes Instructions

You are assisting with the AI-NER-System project.

These instructions define the safe working rules for Hermes Agent in this repository.

---

## Project boundaries

- Work only inside this repository.
- Do not access production servers.
- Do not use UiB credentials, SSH keys, certificates, tokens, or private datasets.
- Do not call external paid APIs unless explicitly instructed.
- Use synthetic or tiny sanitized sample texts for tests.

## Authoritative Docker test baseline

The authoritative local full test workflow is:

```bash
./scripts/test-docker-host-user.sh
```

However, this command must be run from Rui's macOS host terminal, not from inside the Hermes Docker backend.

Reason:

- Hermes terminal commands run inside a Docker backend container.
- `scripts/test-docker-host-user.sh` itself calls Docker.
- The Hermes Docker backend does not have access to the macOS Docker CLI/daemon.
- We intentionally do not mount the host Docker socket into Hermes for security reasons.

Correct workflow:

1. Hermes plans the test and asks Rui to run it from the macOS host terminal.
2. Rui runs:

   ```bash
   cd /Users/ruiwang/Workspace/uib/hermes-sandboxes/AI-NRE-System-Harness-Sandbox
   ./scripts/test-docker-host-user.sh
   ```

3. The script writes result files into `.test-results/`.
4. Hermes reads `.test-results/latest-full-test.md` or `.test-results/latest-full-test.json`.
5. Hermes uses those files to update `testing-status.md` or prepare a PR summary.

Hermes should not run `./scripts/test-docker-host-user.sh` inside its Docker backend.

## Non-authoritative test results

A test result is not authoritative if:

- it was produced by running `uv run pytest` inside the Hermes Docker backend
- it was produced after `ERROR: docker command not found`
- it was produced by a root Docker container
- it used a different Docker image without explanation
- it used partial `PYTEST_ARGS` but is presented as the full baseline
- it came from an unknown environment

If Hermes sees:

```text
ERROR: docker command not found.
```

then the preferred Docker host-user test did not run. Hermes should ask Rui to run the script from the macOS host terminal.

A fallback `uv run pytest` inside Hermes may be useful as a non-authoritative diagnostic check, but it must not be used as the official baseline in `testing-status.md`.

## Known permission-test issue

Running tests as root inside Docker can cause false permission-related failures, especially around unreadable files or unwritable directories.

Known examples include tests such as:

```text
test_validate_input_file_not_readable
test_validate_output_directory_not_writable
test_stream_records_handles_os_error
test_append_text_output_handles_permission_error
```

If these fail in a root container or Hermes backend fallback environment, do not immediately treat them as product failures. Verify using the authoritative host-user Docker test workflow.

3. Update only `testing-status.md`.
4. Do not edit source code or tests.
5. Do not invent test results.
6. Clearly distinguish:
   - functional test result
   - coverage result
   - coverage gate status
   - whether the result is authoritative

```text

```

then record it as:

```text

```
